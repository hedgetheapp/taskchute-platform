## Approved product behavior

1. On Android Today, the current ordinary Running task's panel displays a clearly labeled `割込` action. A single tap initiates Quick Interrupt immediately, without confirmation or title-entry form. Show pending/failure feedback; never display confirmed success until canonical Day reconciliation.
2. Create a new ordinary current-Day Task and Entry titled **`（割込）`** and start its Execution as the interruption target. Its title remains editable while Running via the existing editor. Retain an explicit durable Quick-Interrupt origin independent of title renaming.
3. End the previous ordinary active Execution with **interrupted**, not completed, preserving its historical facts. Create one planned continuation of the previous logical work; do not automatically start that continuation after the new Task completes. Preserve chain identity, original-estimate/actual semantics, and historical snapshots according to D-028 / D-073 where applicable.
4. New Quick Task defaults: **no implicit Project, Mode, Note, reminder, or estimate**. Do not inherit these from the interrupted task. Resolve current Section from the server-authoritative interruption instant and frozen current-Day Section context; do not infer it from client clock, selected Section, or stale previous placement. If unique valid context cannot be proven, fail closed with actionable feedback and no mutation.
5. First slice eligibility: **established current logical Day, ordinary active Running source, authenticated online operation only**. Routine-derived source, non-current Day / cross-Day active Running, unsafe/missing identities and unresolved operations are ineligible; do not silently broaden D-073's current restrictions.
6. Repeated Quick Interrupt while the new ordinary Quick Task is Running is allowed without an arbitrary nesting limit. Each interrupt creates its own planned continuation and keeps actual history. There is no auto-resume. Except for the explicitly approved local Quick target/continuation adjacency below, broader grouping/priority behavior for multiple continuations is **not approved**.
7. Error/retry is an **online, in-memory exact-operation retry** first slice. Retain the same immutable request identifiers/payload across ambiguous retries during the same live session; reconcile against canonical server state. Automatic process-death recovery, offline queue, and a new operation-lookup endpoint are outside v0.1.

## 2026-10-21 follow-up — Option A: Quick continuation directly below its interrupt target (Approved)

The Product Owner explicitly selected **Option A** after Codex identified the D-028 vs D-081 projection conflict and stopped. This is a **Quick Interrupt-only exception to the D-081 execution-first display order**, not a change to ordinary D-073 Interrupt placement, the historical Execution facts, or other Planned ordering.

- If one Quick Interrupt atomically interrupts ordinary A, creates and starts Quick target B, and creates Planned continuation C of A, display **C immediately below B in the same Section** on the canonical Day/Today projection whenever **B is visible and C is still Planned**. Preserve this adjacency after B normally completes, so the user can choose to resume A manually. **Do not auto-start C.**
- Keep B at its canonical historical position in its Section (D-081 chronological relative order among historical rows); insert the paired C visually immediately after B **exactly once**, excluding C from the remainder of the ordinary Planned group. Other historical rows retain their mutual order; all unrelated Planned rows retain their mutual D-043/D-081 order. This scoped interleaving is the sole exception to the global historical-prefix / Planned-suffix presentation invariant.
- Pair B with **the exact C created by that Quick operation** using durable owner-scoped canonical identity/correlation, not Task title, matching names, neighboring physical positions, client timestamps, or guesswork. Renaming B or C, refreshing, cross-client reload, and exact-operation replay must not lose or duplicate the link. Any minimal new persisted Quick-origin/pair relation necessary for this is within D-181's already-approved backward-compatible APP migration; do not invent legacy links.
- Multiple sequential Quick Interrupts apply the **same independent one-target/one-continuation visual rule**. Do not add nesting indentation, stack priority, collapsing, automatic selection, or auto-resume, and do not reorder unrelated historical anchors. If an anchor B becomes interrupted by another Quick operation, it remains a historical anchor for its own existing C while the later Quick target receives its separately paired continuation.
- If B is not displayed (for example because Completed rows are hidden) or is absent, **C remains visible in the ordinary Planned group** at its canonical Planned placement; it must not disappear or be attached to a different row. If C ceases to be Planned, do not force it into a special slot; the normal historical/current lifecycle projection applies. No visual pairing may manufacture an Execution fact or change Entry lifecycle.
- D-028's Quick-specific **persisted explicit B-then-C placement** and **no automatically populated continuation planned-start value** remain authoritative. D-073's different same-minute/cohort and continuation planned-start rules apply only to its existing ordinary planned-B interruption, **not Quick**. The Quick adjacency exception concerns the **visible/canonical projection**, not a license to change unrelated physical positions or the D-081 command/reorder safety boundary.
- Apply a consistent canonical presentation order across supported Day clients consuming the server Day projection (including Android and Web). Avoid a phone-only sort that disagrees with the authoritative Day response. If required persistence or projection changes violate existing atomicity, ownership, compatibility, or protected historic-position semantics, STOP with the exact conflict.

Acceptance: when other Planned rows already exist in B's Section, the user sees **B → C → other Planned work**, independent of those rows' planned-start cohort. An unrelated ordinary D-073 interruption continues to use its existing D-073/D-081 order; title edits and Completed-hide do not corrupt or lose C. Cover Running/Completed B, multiple Quick operations, completed-hidden, no duplicate C, and canonical Web/Android convergence using focused tests.

## 2026-10-21 Android responsiveness corrective — Approved user feedback (implementation pending)

The Product Owner's Galaxy S23 representative observation is that immediately after ordinary Task Start the bottom Running progress panel appears **before** the `割込` action, which only appears after several seconds; tapping `割込` shows an unwanted `割り込みを処理しています…` sentence and a perceptible delay before the next state.

The approved UX corrective is:
- On an eligible ordinary current-Day Task Start, render the Quick Interrupt affordance **at the same time as the bottom Running/progress panel**. Avoid the late-arriving/relayout button. Eligibility and ability to dispatch the server operation remain distinct: if Start is not yet canonically confirmed, the client must retain the user's Quick intent and await safe canonical identifiers before sending `QuickInterruptEntry`; if Start fails/stales, cancel the dependent Quick intent without generating facts. Keep safeguards for Routine, cross-Day, unresolved, stale identity, and double-tap.
- Remove the ordinary in-progress textual message `割り込みを処理しています…`. Instead give immediate, compact, nonblocking inline response to the tap (e.g. a pressed/pending button state) with accessibility semantics; explicit error, authentication, and exact retry messages still appear when needed.
- Minimize observable response latency and needless round-trips using safe UI-local provisional state and canonical reconciliation. The server remains the authority for Quick Task/Execution/Section/continuation; never imply a committed success before canonical proof or fabricate destructive history. Preserve D-181 atomic exactly-once behavior, immutable retry envelope, and owner/isolation guard. Document actual timing measurements rather than promising zero network latency.
- The request to delete a `中断タスク` is recorded as a **separate unresolved destructive-behavior issue**. Existing `DeleteCompletedEntry` deliberately rejects Entries belonging to a continuation chain; distinguish deletion of the interrupted source history, the Quick target, and the planned continuation. Do not bypass chain guards, delete executions, unlink pairs, or broaden hard-delete until the Product Owner approves exact deletion semantics. Research and propose safe behavior separately.

## Approved technical boundary

- **One new dedicated server command/API and the necessary backward-compatible APP migration are authorized**, including an operations command allow-list extension and minimal persisted Quick-origin/atomicity guard data if required. Exact SQL columns and index/guard layout are implementation details only so long as semantics, old data and compatibility remain intact.
- A single guarded atomic D1 outcome must create the Quick Task/Entry, end source as interrupted, start exactly one target Execution, create source continuation, update placement revision as required, and durably store the operation result. No partial Task/Entry/Execution/continuation or mixed visible state is permitted.
- Enforce authenticated owner/Day/active-execution/source identity, placement revision, target ID collisions, unique active Execution, and transaction invariants. Preserve operation ID fingerprinting, exact replay, misuse rejection, ambiguity recovery, and concurrent-client convergence. The existing D-073 `InterruptEntry` API and historical data remain backward compatible.
- Server contract, APP migration, Android repository/controller/presentation, and impacted focused tests are in-scope. Persistent nonprod backup/migration/deploy/verification may proceed under the existing governance hard gates. Production, restore, branch/PR/merge/tag/release, new recurring-cost dependencies and destructive changes remain out of scope.
- D-028's Quick-specific physical continuation placement/planned-start meaning remains authoritative; the **2026-10-21 Option A decision above explicitly resolves only the previously stopped Quick display-order conflict with D-081**. Any additional Material Product choice or incompatible historic-position constraint still requires STOP, not an implicit SPEC rewrite.

## Acceptance / evidence

- Android: ordinary Running → one tap `割込` → canonical `（割込）` Running, source interrupted, one planned continuation; title editable while Running; normal completion does not auto-start old work.
- Worker/D1: exact replay, conflicting fingerprint, stale active/revision, owner mismatch, duplicate IDs, concurrent callers, Section resolution, transaction failure with zero partial writes, and no more than one active Execution. Cover repeated Quick Interrupt and existing D-073 regression.
- Migration: both fresh install and upgrade with existing operations/Entries/Executions intact, no manufactured historical origins or outcomes. Observe `TEST_MATRIX` statuses separately for Implemented, Integrated, Tested, Verified and Released.
- Tests are impact-based/focused rather than all suites by default. Verify exact implementation commit in CI. Obtain the signed **Phone APK from that exact commit** for direct ChatGPT handoff; report nonprod/production/device evidence honestly.
