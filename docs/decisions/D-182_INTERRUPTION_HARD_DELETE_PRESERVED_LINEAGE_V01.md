# D-182 — Interruption-related Entry hard delete with non-visible surviving lineage v0.1

**Status:** Approved (Product decision; implementation not started)
**Approval:** 2026-10-21, Product Owner: requested that all three interruption-related Task rows be deletable, selected **Option A (delete Entry and its actual history, not hide)**, then explicitly approved the proposed **minimal non-visible lineage metadata** approach and a scoped APP migration/nonprod-first verification.
**Source of truth:** This Decision, `docs/DECISIONS.md`, `docs/SPEC.md`, `docs/ARCHITECTURE.md`; code and `docs/TEST_MATRIX.md` determine implementation/verification status.
**Basis:** D-016 (historical facts), D-028 / D-073 (interrupt / continuation / baseline estimates), D-067 / D-128 / D-174 (single-Entry corrections), D-178 (Review), D-181 (Quick / pairing), and `docs/planning/2026-10-21_D181_RESPONSIVENESS_AND_HARD_DELETE_FOLLOWUP.md`.

## Product decision

An explicitly user-confirmed **Delete** on an eligible interruption-related row **hard-deletes exactly that selected Entry and its own Execution facts**. It is not a display-only hide/archive. The selected Entry contributes no Completed/unexecuted count or actual duration to the Day/Review after canonical success. **Unrelated Entries, their Executions and historical snapshots, and surviving continuation Entries are never implicitly deleted or completed.** This is a narrow explicit correction exception to the general historical-preservation posture in D-016, analogous to D-067, and does **not** authorize bulk deletion of historical chains.

Eligible row classes:
1. **A — interrupted source:** a completed/terminal Entry whose Execution ended `interrupted`, even if its continuation survives.
2. **C — generated continuation:** a Planned continuation or an eligible subsequently Running/Completed continuation, **including when it has descendants**; user can select and delete this Entry alone.
3. **B — Quick-created target:** a Quick Interrupt target that is Running/Completed and eligible for single-row correction, including if later interrupted and its own continuation survives. Ordinary D-073 targets continue to obey their own regular Entry/delete authority; this Decision does not broaden Routine or future-Day executions.

Support the established current Day and **eligible established past Day single-row corrections** under existing D-174 conditions. No synthetic past Day establishment, unspecified future/cross-Day mutation, bulk Running/Completed delete, Routine Definition/Occurrence deletion, unapproved Document deletion, generic archival, or undo is added. The Android existing `その他 → 削除` path and its explicit destructive confirmation are retained; hiding or suppressing a refused action must never imply the target was removed.

### Surviving lineage and baseline

**Option approved:** Preserve the necessary lineage identity and original chain baseline in **minimal, owner-scoped, non-visible persisted metadata** whenever a deleted Entry has surviving descendants, instead of re-rooting or rewriting the surviving Entries' historical parent/root identities.

- Deleting A or an intermediate C removes its Entry, its Executions and Entry-local relations/snapshots only. The retained lineage metadata represents **structural ancestry and the original nullable chain estimate baseline**, not a surrogate Execution or a visible Task. It must never preserve removed actual duration, completed status, historical title/contents, or create fictitious Completion/Review outcomes. Keep owner, stable chain/root identity and necessary deleted-node→parent identity for surviving descendants; avoid retaining unnecessary personally identifying payload.
- Surviving Entries retain their own stable Entry/Task identity, placement, Day, lifecycle, own Executions, existing snapshots, and lineage references. A descendant's parent may resolve to a **non-visible lineage node**, not a live Entry, and this must be explicitly validated by a canonical owner-scoped integrity check. Do not silently turn an orphaned parent into a different real Entry or invent historical order.
- Preserve the original baseline estimate **only while at least one live member of the work chain requires it**. For prospective chain calculations and Review's single-chain baseline convention, derive actual work only from **surviving valid Execution facts**. Deleting an Entry removes its own actual seconds and Completed result from all impacted period/category Review projections; do not rewrite survivor actuals. The retained baseline does **not** count as a deleted Entry, completed row, executed time, or additional work chain. If no live chain members require the lineage, retained lineage metadata must not appear or count in Review; bounded garbage-collection details are delegated only when safe for exact replay and compatibility.
- Never silently overwrite a surviving Entry's **explicit user-entered estimate**. If current source representation cannot distinguish a calculated continuation estimate from a user-edited estimate, do not speculate or fabricate a new value. Preserve authoritative Entry fields and report any material user-visible estimate/Review conflict as a **STOP** before implementation of that path. Verify the future Quick/D-073 continuation-estimate algorithm can resolve the retained root baseline without accidentally counting deleted actuals.

### Quick B→C presentation relation

If the user deletes either endpoint of an existing `quick_interrupt_entry_pairs` record, **remove that visible B→C pairing** (existing owner-scoped cascade behavior may be reused after safety proof); no historical pair tombstone is required. If B was deleted while C survives, C remains an **ordinary visible Planned continuation** in its canonical Planned position, or follows its normal lifecycle order if already started. If C was deleted while B survives, B and its own Execution remain. A deleted A does **not** erase the B→C pair if B and C both survive. Repeated Quick Interrupt pairs and nested/branched chains must apply the same endpoint rule independently. No auto-resume, reparented live Entry, new stack priority, or other historical UI is introduced.

### Persistence / safety authority

**Approved technical envelope:** One **additive, backward-compatible APP D1 migration** for the minimal lineage/root-baseline record(s), owner-scoped integrity constraints and indexes, plus any narrowly necessary guard, operation allow-list, or pairing-safety adaptation; no AUTH migration, legacy backfill/re-rooting, destructive bulk schema rewrite, unrelated data mutation, new long-lived dependency, or significant recurring cost/security-posture expansion. Exact table names, columns and transaction details are implementer-delegated only within this envelope.

- May safely extend existing D-067/D-128/D-174 guarded single-Entry endpoints or add **one narrow dedicated chain-aware delete command/API** if required for old-client compatibility; preserve existing routes, request/result families, immutable sent-operation fingerprint/replay and historical successful outcomes. Do not globally loosen singleton-chain guards. Existing planned delete must not be used to bypass lineage/protected-history checks.
- Atomic D1 mutation must verify authenticated owner, exact established Day/Entry, lifecycle/Execution invariants, current active Execution where applicable, affected chain members, surviving ancestors/descendants and Quick pair edges, CAS placement revision, and dependent references at commit. A changed target/chain/pair, stale revision, owner mismatch, active anomaly or unsafe future Routine/Document relation rejects **with zero partial writes**.
- Delete target Executions and Entry-bound rows in an FK-safe order and preserve all other Entry/Execution facts. Record/replay the exact result once; simultaneous identical retries converge, conflicting fingerprints fail, unexpected D1 errors remain ambiguous rather than confirmed success. Do not leave dangling active Execution, visible duplicate continuation, invalid tombstone resolution, or inaccurate future estimate/Review.
- If unexpected legacy rows, corrupted/dangling chains, replay gaps, migration ordering, D1 transactional limits, or new Material schema/security/cost/compatibility choices prevent meeting this contract, **STOP before write** and present concrete alternatives. Never reinterpret missing history as a verified estimate or synthetic parent.

### Rollout and verification boundaries

- Codex may perform approved code, focused tests, safe fast-forward push, and **persistent nonprod** backup/recovery **validation (not restore)**, approved APP migration and exact Worker deployment after standard gates. Use only an isolated previously approved nonprod QA owner plus newly created, disposable synthetic test Entries for destructive API tests; never delete dogfood/real-user records or the existing D-178 fixture account/coverage marker. Production mutation, migration, deploy, restore, destructive removal of unrelated records, branch/PR/merge/tag/Release are outside approval.
- Focused tests must cover A-with-C root deletion, C leaf and middle deletion, B singleton and B-with-continuation deletion, repeated/nested Quick, ordinary D-073 continuation, past/current, both B→C endpoint deletions, surviving direct-below/fallback ordering, nullable baseline, explicit estimate preservation, exact Review count/time and period/category updates, no auto-resume, owner/revision/operation replay/parallel collisions, rollback/fault injection, legacy migration upgrade/fresh, no partial writes, one active Execution max, APP/AUTH D1 integrity, and the Android confirmation/eligible action. Test only impact-appropriate scopes, not the full suite by default.
- Android change requires an **exact implementation-SHA signed Phone APK** handed directly to the user by ChatGPT. The latest responsiveness-only APK `e53fd8d…` does not implement deletion and cannot substitute for it.
- `Implemented`, `Integrated`, `Tested`, `Verified`, `Released` are distinct. Product Verified/Released remain **NO** until independent required evidence. Unperformed browser/Galaxy S23/production checks remain `NOT_RUN`.

## Explicitly deferred

General-purpose bulk history deletion, deletion of unrelated protected references, automatic cascade across chains, restoration/undo, Routine-aware interruption, auto-resume, production rollout, implicit ancestry rewriting, historical content retention, and additional user-visible Review semantics not established above are **not approved**. New Material Decision => STOP.
