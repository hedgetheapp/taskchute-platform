## User-visible request

The Product Owner wants Section headers to show the whole Section's task count, completed-task count, and remaining time. Example:

`09:00-12:00 セクション名 (4/10件 1h20m)`

Interpret the requested `4/10` as **4 Completed out of 10 assigned entries**. The Product Owner selected **remaining estimated task workload**, dynamically decreasing for an active Running task, not elapsed clock time remaining until Section end.

Initial scope assumption from discussion context: **Android Today Section headers**; Web/Wear parity not yet decided. No implementation requested while travelling.

## Current source and canonical considerations

- Android `TodayScreen.kt` `SectionHeader` currently renders a 38dp single-line header with collapse arrow, time range, Section title and optional D-161/D-165 warning. Space is constrained and warning visibility must not regress.
- `TodayModels.kt` `TodaySection.entries` contains the Section's Planned / Running / Completed `TodayTask` entries with Entry estimate and execution information. `TodayDay.unsectionedEntries` is separate.
- D-162 `完了タスクを表示` hides completed **rows only**; does not alter Sections, canonical entries, forecasts or warnings. Header summary should therefore be independent of the hide/show preference, if that behavior is approved.
- D-134 Running progress uses `max(0, estimate - elapsed)`, with separate overrun indication. D-173B cross-Day active entries remain outside current Day rows, so do not silently add them to current-Day Section counts.
- D-161 / D-165 Section forecast warnings and precision are existing independent indications; do not conflate them with remaining workload.
- D-178 Review analytics have a different period/Completed projection; this proposal should not claim Review historical facts from approximate current Section workload.

## Proposed behavior for Product decision

1. Per selected established Day Section, summarize **currently assigned Entries**. `completed/total件` uses Completed count / all Planned+Running+Completed count, not Task Definition count or history of moved/deleted assignments. Routine occurrences and ordinary Entries each count as assigned Entries when present.
2. Same Section summary stays visible even while Section is collapsed or Completed rows are hidden by D-162; it updates after confirmed canonical changes in status/placement/delete and can use existing carefully reconciled optimistic presentation where safe.
3. **Agreed direction (2026-10-17):** display **dynamic remaining estimated workload**, not the wall-clock time until Section end. Completed contributes 0; Planned with an estimate contributes its full estimate; the active Running task with an estimate contributes `max(0, estimate - elapsed)` and this portion decreases as the Execution progresses. Estimate value itself is not mutated. At or beyond estimate, Running contributes 0 (never negative), while Completed count increases only on actual completion. Whether a Running Entry whose active Execution belongs to another logical Day participates in its owning Day needs verification.
4. **Agreed direction (2026-10-17):** when at least one incomplete (Planned/Running) Entry has no estimate, display the **sum of known remaining estimates with a trailing `+`**, e.g. two known tasks totaling 40m and one unknown-estimate task → `40m+`. The `+` signals unquantified additional work, not an exact complete total. Do not treat missing estimates as estimated 0. If no unfinished Entry has an unknown estimate, omit the `+`.
5. **Updated layout direction from Product Owner (2026-10-17):** **withdraw the earlier no-space time-range suggestion** and retain the already approved visible time format `09:00 - 12:00` (`HH:mm - HH:mm`). **Explore a two-line Section header** instead of compressing everything onto one line: first line contains the existing collapse/expand indicator, `HH:mm - HH:mm`, and Section name. **New requested visual (2026-10-17):** add a *progress bar / 進捗バー* immediately **before** the completed/total task count on the second line, then show the dynamic remaining time to its right. Proposed presentation: `[progress bar] [check_circle icon] 4/10件 [hourglass icon] 1h20m`. **Historical 2026-10-17 choice, SUPERSEDED on 2026-10-18:** bar width originally matched only the remaining duration text (`1h20m`). The canonical D-180 visual corrective instead requires the bar to match the **entire first-line Section time-range text width** (`09:00 - 12:00`), from the first glyph of the start time to the last glyph of the end time. Do not stretch the bar across the remaining row width; keep bar → completion icon/count → hourglass icon/time in order. **Updated alignment choice (2026-10-17): do not right-align the second row. Align the left edge of the progress bar with the left edge of the FIRST line's time-range text (`09:00`), and flow the completion icon/count and remaining-duration icon/text naturally to the right. A user-configured custom Section icon (see linked Section icon planning note) sits between the collapse chevron and the time range, so the second-row bar must start after BOTH the chevron and the custom icon; never align to the custom icon's left edge. Without a custom icon, retain alignment to the time text.** This replaces the right-aligned illustration; preserve bar width equal to the first-line time-range text bounds, regardless of the remaining-duration label. Use the actual first-line range text layout bounds for width so updates to remaining time (`40m+`, `12h00m`) do not resize the bar. **Product Owner request (2026-10-17):** place an appropriate compact icon immediately before the task count; **recommended** use the existing Material `check_circle` completion motif in subdued secondary color, approximately 14–16dp, consistent with task completion visuals. This particular icon/color/size is an illustrative UI recommendation, not a new Product semantic. Do not place the icon before the progress bar; keep it between bar and `4/10件`. **Approved (Product Owner 2026-10-18, D-180) progress semantics:** bar fill is Completed Entry count / currently assigned Entry count (4/10 = 40%), independent of dynamic remaining estimated time. Running does not increase bar fill until Completed. **Historical Stage 1 convention (superseded on 2026-10-18):** zero assigned Entries formerly displayed an empty bar. The Product Owner now approves **0/0件 → 100% full bar**, without fabricating Completed entries; see canonical D-180 follow-up. Keep summary accessible when collapsed/Completed rows hidden; don't conflate overrun or forecast warnings with bar progress. This approved Stage 1 arrangement is implemented as recorded in `docs/CURRENT.md` and `docs/TEST_MATRIX.md`. Existing Section warnings (D-161/D-165) remain independently meaningful and must stay accessible; the implementation verified their visibility at default and narrow-width/large-text AVD settings.
6. `セクションなし` group, empty Sections (`0/0件`), current/future/past Days, and unknown estimate cases require appropriate fallback rules. No DB write or mutation for display-only aggregation.

## Open questions

- **Resolved (Product Owner, 2026-10-17):** Option A, **dynamic remaining estimated workload**. Running's remaining portion decreases over time; it is not Section clock time, and its configured estimate itself does not change.
- **Resolved (Product Owner, 2026-10-17):** for one or more incomplete Tasks with unknown estimates, show the known remaining-work subtotal plus `+` (e.g. `40m+`), instead of hiding the entire time value (`--`).
- **Resolved by D-180 implementation:** the lightweight UI-local clock updates the active Section workload; positive partial minutes round up, values clamp at zero, and an unknown unfinished estimate with no known subtotal displays `0m+`. These are presentation details within the approved semantics.
- **Resolved:** retain the original spaced Section range `09:00 - 12:00`; the intermediate `09:00-12:00` experiment was withdrawn by the Product Owner. D-180 approves and the implementation uses the two-line Section header with time/name on row 1 and progress bar → completion count → dynamic remaining workload on row 2. **2026-10-18 revised width:** the bar's visible length matches the complete time-range **`09:00 - 12:00` text** width, left and right aligned to its actual glyph/text bounds, not to the duration text and not flexing to the row width; implemented at `af83b64a2f4d59910d30c0d694ff1109e2a36a0f`. The original duration-text-width rule is superseded. Progress fill = Completed Entry count / total assigned Entry count, with the approved `0/0=100%` convention and visually continuous track implemented at `a6d231404e1526832b6d9fe1d653c85555717656`. Warning semantics remain D-161/D-165; visibility passed at narrow width and larger text. The `セクションなし` summary remains deferred.
- **Resolved by D-180:** first stage is Android Today configured timed Sections only. Whether the unsectioned group should receive a summary remains open for later Product decision.

## 2026-10-18 follow-up — bar-width geometric correction

After testing D-180 on the phone, the Product Owner requested a longer bar: **the progress bar must begin at the first `0` of `09:00` and end at the last `0` of `12:00`**, i.e. the entire rendered spaced time range `09:00 - 12:00`. The previous text-only duration-width rule is superseded. The display remains **two lines**: line 1 = chevron, time range, title / existing warning; line 2 = progress bar, completion icon/count, hourglass/remaining time. A former chat mock inadvertently put remaining duration on a third line and was corrected. Bar fill remains Completed/Total (e.g. 4/10 = 40%), and icon storage, Sectionless summary and any underlying write semantics are unchanged. Canonical authority: `docs/decisions/D-180_ANDROID_SECTION_HEADER_PROGRESS_V01.md`. Implemented at `af83b64a2f4d59910d30c0d694ff1109e2a36a0f`.

## 2026-10-18 follow-up — empty Section fully filled and gapless bar (APPROVED / IMPLEMENTED)

After viewing the Galaxy S23 implementation, the Product Owner identified two issues: `0/0件` had an empty/unfilled bar, and the progress line looked visually split (`---|-----`). On 2026-10-18 the Product Owner approved **`0/0件` = 100% full bar** and **one unbroken progress line** with no deliberate gap/stop marker. Counts do not change; `0/5` = 0%, `2/5` = 40%, `5/5` = 100%; maintain the bar's width equal to the first-line full time-range text, all second-row items, and existing warnings and hit geometry. Implemented at `a6d231404e1526832b6d9fe1d653c85555717656`; focused JVM and AVD pixel evidence passed. The historical `0/0=0%` assertion is invalidated by the revised contract and was replaced by passing `0/0=1.0` coverage. Exact evidence is in `docs/CURRENT.md` and `docs/TEST_MATRIX.md`.
