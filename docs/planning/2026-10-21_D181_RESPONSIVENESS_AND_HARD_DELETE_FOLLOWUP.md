## Read-only hard-delete findings

The Android menu and the Worker guard are separate. On Today, a current ordinary interrupted A or Quick B in Running/Completed state can show `その他 → 削除`; ordinary Planned C can use the current-Day planned delete entry point. Past lifecycle rows and a past Planned row also have UI affordances. A row being visible does not mean the server will accept a chain mutation.

| Case | Existing behavior and invariant | Design-gate result |
|---|---|---|
| Interrupted A with surviving C or descendants | `DeleteCompletedEntry` requires a singleton chain: `continuation_chain_id = entry.id`, no parent, and chain count `1`. A is the chain root and C remains in that chain, so the guard rejects it. Removing A would also remove its Execution actuals and the only root estimate source used by D-073 / D-181 continuation estimate calculation. Survivors would retain A's chain ID and parent identity. | Not safe under the existing contract. Choosing a new root, transferring a baseline, or retaining detached chain metadata changes persisted history and Review semantics. Already-started C with later descendants adds parent/chain rewrites. |
| Planned C, no descendants | Current-Day ordinary Planned deletion uses `BulkDeleteEntries`, requires no Execution history, checks owner/Day/revision and snapshots target placement/chain state, then deletes the row. The singleton-chain guard is specifically applied to the past single-row path; past C in A's chain is rejected. Migration `0039` gives the B→C pair `ON DELETE CASCADE` from either endpoint. Deleting current C therefore removes that pair row while leaving B and its Execution; deleting B through its eligible singleton path leaves C as an ordinary Planned row. | The current-Day Planned leaf path appears reusable for the visible row outcome, but pair-history removal is not a selected product rule and was not exercised in a delete test. Past C remains blocked. |
| C with descendants | Once C has been interrupted to create a descendant, C is no longer Planned. Lifecycle deletion reaches the singleton-chain guard and is rejected. Its child points to C and the original chain baseline remains at A. | Not safe without approved re-parenting or a non-visible lineage record, plus an atomic Review/actual policy. |
| Quick target B, before it becomes a source | D-181 creates B in its own singleton continuation chain and stores the separate immutable B→C pair. Current or past Running/Completed B can pass the chain-shape guard if other lifecycle and protected-link checks pass. The delete command removes B's own Executions and Entry-bound snapshots; deleting B cascades the pair row under the existing `0039` foreign key, so surviving C falls back to normal Planned order. | Existing singleton path can plausibly satisfy the visible target/actual outcome, subject to accepting pair removal and verifying all guards. Not exercised here. |
| Quick target B later interrupted as a source | A later continuation joins B's chain and makes B a non-singleton root. `DeleteCompletedEntry` rejects B. Re-rooting the later continuation would alter parent/root-estimate semantics; deleting B also removes any earlier B→C pair by cascade. | Not safe under the existing contract. Requires the same root-baseline decision as A plus the pair rule. |
| D-073, metadata, Routine/future links, replay | The reused lifecycle command checks authenticated owner, exact Day/Entry, lifecycle/Execution state, placement revision and chain shape again in its guarded D1 batch. It deletes the selected Entry's Executions and Entry-bound guards/snapshots/relations, increments the Day revision, asserts the target and its Executions are absent, and retains the `operations` replay row. Task/Project/Mode/Routine definitions and other Entries are not deleted. Existing suppression and completed-entry→future-Routine guards remain. | Do not weaken D-016 or remove the chain guard globally. Any extension must also snapshot/check paired rows and the full affected chain in the guarded transaction, retain exact replay, and prove rollback and one-active-Execution invariants. |

`0023_interrupt_continuation.sql` stores chain ID and parent ID as plain text, without a root/parent foreign key. `0039_quick_interrupt.sql` adds the pair foreign keys with cascade deletion, but no pair tombstone. The plain-text chain columns therefore do not prevent dangling ancestry by FK; the current Worker guards are the protection. The Quick create command derives a continuation estimate from the chain-root Entry's estimate and the sum of chain Execution actuals. Review actuals are backed by Execution rows, so deleting the selected Entry's own Execution naturally removes those actuals; deleting the root also removes the current estimate source. `DeleteCompletedEntry` explicitly cleans target snapshots before removing the Entry; the planned delete path is narrower and is not a substitute for lifecycle chain deletion.

These are source/schema findings, not an assertion that a remote delete, pair cascade, Review projection, or concurrent delete was executed. No destructive fixture was created for this investigation.

## Material decisions required before deletion implementation

1. **Deleting a chain root with survivors:** choose (a) retain a non-visible chain-root/baseline tombstone independent of the deleted Entry and Execution; (b) re-root the surviving chain at its oldest surviving Entry and explicitly choose whether its baseline is the original estimate or the remaining estimate, with an approved Review result; or (c) keep chained roots protected, which does not fulfill independent deletion of all approved categories.
2. **Deleting a continuation with descendants:** choose between atomically re-parenting its surviving descendants (and accept the rewritten ancestry) or retaining a non-visible lineage node/tombstone. Define how the deleted node's own actuals are removed while the chain baseline and later actuals remain coherent.
3. **Deleting Quick target B:** choose whether the existing `0039` FK cascade permanently removes B→C pairing and C becomes an ordinary Planned row, or preserve a non-visible historical pair tombstone while still rendering C normally. The user-facing fallback is clear; the retained historical relation is not selected.

Recommendation: decide the chain-root and descendant lineage model first, then approve the pair-removal rule. If preserving the current chain baseline and parent history is required, a small owner-scoped non-visible chain metadata/lineage representation is safer than rewriting unrelated surviving Entries, but it requires an additive APP migration and an explicit retention meaning. Either implementation must use a guarded atomic transaction that re-reads the affected chain and pair edges, validates exact owner/Day/revision and active Execution, records the existing operation result, removes only the selected Entry's Executions, verifies survivor lineage and Review consequences, and rejects stale concurrent callers. Keep the existing request/response and exact replay compatibility for old Android clients. A future nonprod rollout needs the normal backup/migration/Worker compatibility gate; no such rollout is authorized by this report.

Until those choices are approved, do not add a migration, alter protected chain meaning, remove the server guard, test with real hard deletes, or claim A/C/B hard delete support.
